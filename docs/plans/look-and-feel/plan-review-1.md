# Plan review: Claude Code look and feel (status line redesign + `look` band mod)
Verdict: PASS WITH CHANGES
Summary: The scope is coherent and fits a solo, no-deadline schedule. Several things need fixing before handoff. The status line redesign silently drops features the current script has and its tests assert. The plan's own research says timers are dropped on hot reload, which conflicts with starting them only in `session.start`. Items have no stale or dismiss semantics, so a lost notification or a branch switch leaves the band stuck. The backup alert duplicates an existing hook with different rules. One caveat: the mod API reference given as input (`/tmp/claude-1000/bundled-skills/2.1.304/...`) no longer exists. Searching `/tmp/claude-1000`, `~/.claude` and `~/.cache` found no copy. So every API claim in "## Research" is unverified by this review. Installed Claude Code is already 2.1.305, not the 2.1.304 the plan was built against.

## Unnamed risks
- The mod API changes under you. The plan was built against 2.1.304, 2.1.305 is already installed, and the research source in `/tmp` has already been deleted. Likelihood: high. Mitigation: commit the relevant `.d.ts` excerpt (or record the version and hash) in the plugin. Guard every API use with feature checks so a missing API draws nothing instead of throwing. Add a version line to docs/look.md.
- A mod error breaks the prompt area or spams errors on every redraw. Likelihood: medium. Mitigation: wrap render and poll handlers in try/catch, fall back to `next(e)`, and log once.
- Several Claude sessions (one per zellij pane, via `cz`) each poll `gh` and keep their own alert state. The result is duplicated alerts and API calls. Likelihood: high. Mitigation: share the CI poll result and its dismissal through `$.store` with a timestamp, so only one session polls per interval.
- With Strict TDD, background `make check` runs fail on purpose during the red phase. Each failure pins a red alert, which causes alert fatigue. Likelihood: high. Mitigation: see question 2.
- Mod tests cannot run in the Arch CI container, so band regressions only surface on the local machine. Likelihood: medium. Mitigation: install a pinned Claude Code in CI, or accept this and document it.

## Questions for the user (max 5)
1. Are you OK losing the 5h reset time and the zellij session name from the status line, and should the dirty `*` stay? Why it matters: these are existing features with tests and README rows, and the plan removes them silently. Recommendation: keep `*`, show the reset time only when 5h is 80% or more, and drop the zellij name.
2. Should a failed background shell (for example a red `make check` during TDD) pin a red alert, or only show a short failure toast? Why it matters: with Strict TDD, failures are routine. Recommendation: pin only CI, backup and agent failures. Show shell failures as a red toast plus a dim row that clears on the next run of the same command.
3. Should a dismissal (✕) apply to all open sessions or only the current one? Why it matters: you run several sessions in zellij panes, and per-session state means dismissing everywhere. Recommendation: shared through `$.store`, keyed by the failing run or backup timestamp.
4. Should the band's backup alert replace the SessionStart `backup-status` message or sit next to it? Why it matters: two surfaces with different rules will disagree. Recommendation: keep the SessionStart message and make the band SHOULD, alerting only on a failed last run.
5. Is installing Claude Code in the CI container acceptable (a pinned npm or pacman package, with no auth needed for `claude plugin test`)? Why it matters: without it the band has no CI gate. Recommendation: yes, if `claude plugin test` runs offline without an account. Otherwise accept a local-only gate and document it.
