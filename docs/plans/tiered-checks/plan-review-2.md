## Unnamed risks
- Trusted `NOTCH` on a branch without `check-fast` runs the full suite between turns: keyboard grabs, `qs` launch, up to 300 s. Likelihood: high on story 44's branch. Mitigation: finding 1.
- Agents keep running `make check` every turn because AGENTS.md and the templates tell them to, so the measured speed-up never shows. Likelihood: high. Mitigation: finding 2.
- The 10 s budget was measured at load 1.4. With ollama or the NPU busy, shellcheck over a large changed set can blow it. Likelihood: medium. Mitigation: measure `check-fast` once under load in the `AI` story. The 60 s timeout stays the net.
- The full suite approaches the Bash tool's 600 s hard ceiling: 319-325 s with a bench change at load 4-6 (idea 27), now run 2-3 times per high-risk story (pair, verifier, ship). Likelihood: low-medium. Mitigation: allow running it in the background and reading the result, as ship step 5 already does for CI.
- Golden mismatches from skill edits now surface only in the full tier (`gen-agents.test.sh`), not between turns. Likelihood: high, impact low. Mitigation: each skill story runs `bash scripts/tests/gen-agents.test.sh` as its focused test.

## Questions for the user (max 5)
1. Trust `NOTCH` only once `check-fast` is on its `main` and open story branches have merged it? Why it matters: until then, trust makes the hook run the full keyboard-grabbing suite between turns on those branches. Recommendation: yes, and make it an acceptance criterion of the NOTCH story.
2. Should "changed files" for the fast tier include commits not yet on `origin/main`, not just uncommitted changes? Why it matters: under `pair` almost everything is committed, so the fast tier almost never lints story code. Recommendation: uncommitted plus `origin/main...HEAD`, falling back to `HEAD`. It costs a few seconds.
3. Reword the agent rule "Work is done only when `make check` passes" (NOTCH AGENTS.md and the foundation template) to "A story, a ship and CI are done when `make check` passes"? Why it matters: the current wording makes agents run the suite every turn. Recommendation: yes.

Recommendations I resolved myself (technical): define the regression step as an existing failing test followed by a `fix:` commit, with stop rule 3 when the old test must change; rerun the `Test command:` after any step-6 fix; give the verifier the same long-timeout line; pass the changed-files mode through an env var set only by the `check-fast` recipe and lint everything when a sourced lib changes; word the timeout neutrally for the generated targets.
