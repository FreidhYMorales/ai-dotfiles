# Plan review: replace-sdd
Verdict: PASS WITH CHANGES
Summary: The plan holds together and fits the time available (no deadline). Its main gaps are conflicts with machinery already in the repo. The `require-check` Stop hook and the `work-unit-commits` skill both fight the "commit the test before the code" step. Collaborative `split`/`next` need fields that the one-line backlog format cannot hold. Retiring `sdd` does not handle machines that already have it installed. No blockers; several major findings need a small fix each before handoff.

## Unnamed risks
- `require-check` Stop hook overrides the pair stop rules after a red test is committed — high — see finding 1, plus a regression test.
- Red commits on `main` break `git bisect` and per-commit CI; a push between the test and code commits shows CI red — medium — pair on a story branch, or document that pushes happen only after green.
- `work-unit-commits` / `chained-pr` fire during pair and steer it back to combined commits — medium — finding 2.
- In-flight SDD changes in other projects (the plugin is global) are orphaned when `sdd` is uninstalled — low-medium — `rg -l openspec/changes` over the user's projects before story 07; tell the user (Q3).
- Old engram observations (`sdd/{project}/testing-capabilities`, `sdd-init/*`) keep showing up in `mem_search` and steering agents to `/sdd:*` — medium — `flow:backlog` ignores the `sdd/*` topics; note in story 07.
- Skill basename collision in flat OpenCode/Antigravity skill dirs: `backlog`, `story` and `pair` are generic names, and a pack or vendor skill with the same name would shadow them or be backed up as `.bak` — low — check `packs/` and the target dirs in the install test.
- hola-ai licence: the scratchpad copy contains no LICENSE file; MIT is only asserted — low — confirm upstream LICENSE before adapting text; record it in `upstreams.json`.

## Questions for the user (max 5)
1. In collaborative mode, does the backlog also replace `split`'s `tasks.md` (owners, files owned, dev-days, delivered/integrated)? — It decides whether `split`/`next`/`integrate` need a second format. — Recommendation: keep `tasks.md` for collaborative `split`/`integrate` only; the backlog is the solo source.
2. Is it acceptable that pair puts red (`test:`) commits straight on `main`, or should each story run on a branch, possibly squashed at merge? — CI, bisect and the "commit the test first" evidence pull in different directions. — Recommendation: one branch per story, no squash, so the test-first evidence survives.
3. Do any of your other projects have open `openspec/changes/*` or rely on `/sdd:*` today? — Uninstalling the global plugin strands them. — Recommendation: finish or archive them first; story 07 uninstalls only after that.
4. For stories that only change markdown skills (all of this plan), what is the "test" in pair: a bash structural test in `scripts/tests/`, an eval, or both? — Without an answer the dogfood demo has no real red. — Recommendation: a bash structural test as the pair test, with evals as the story's acceptance check.
5. Should `toolkit:work-unit-commits` be changed to accept the test-then-code pair as one work unit, or should pair just override it? — It is an Apache-2.0 upstream skill you track in `upstreams.json`, so editing it adds drift. — Recommendation: add a short exception section, which is less fragile than relying on pair to override it.
