# Plan review: clean-install
Verdict: PASS WITH CHANGES
Summary: There are no blockers, and the MUST scope fits because there is no deadline. Reviews 1 and 2 are mostly resolved, and the MUST total of 16.35 adds up. The new-repo decision from review 2 created problems the plan does not address: what happens to the old clones, a `git revert` fallback whose commit will not exist, a Gmail address still in the public tree, and no home for this plan after stage 3. There are also two gaps in the checks that guard the format.

Limits: I inspected code and live state read-only. I opened no secrets and did not run bootstrap or a VM. The external disk's contents and the base install's default `mkinitcpio` hooks are unverified.

## Unnamed risks
- The VM holds a real `gh` sign-in. If the documented path is followed literally, it clones the real `engram-backup`, and the backup path runs `restic forget --prune` and pushes (`AI/bin/engram-backup:364-365`). The throwaway copy (plan.md:122) means the VM skips this step — low to medium — Point `ENGRAM_BACKUP_REPOS` at a local throwaway repo, disable the backup timers in the VM, and write this down as the one permitted deviation from the documented path.
- A fresh install's default `mkinitcpio` hooks may differ from this machine's `udev`-based line. `bootstrap.sh:577` assumes it can add `resume` after `block`. I could not confirm the current default — medium — Check the hooks in the VM with finding 6, and handle a `systemd`-based line if one appears.
- Public trees keep many dead SHAs in backlogs, story logs and engram memories (for example `NOTCH/docs/plans/notch/backlog.md`), which breaks later history lookups — high likelihood, low damage — Add one line to each README naming the frozen repo as the record. Do not rewrite the SHAs.
- A stale Vesktop `sessionData/` remains inside the SYS working tree through Stow, so a missed ignore rule in a new repo's first commit would publish a Discord session — low — Add the ignore rule before the first `git add`, and review `git ls-files` from the root commit by eye.
- A first-boot fix on the laptop can fail with no agent working, and the checklist's fallback is a redo from the ISO — low to medium — Keep the checklist commands for a second device, and make the plan home (finding 4) readable without the laptop.

## Questions for the user (max 5)
1. Do you want a second copy of the irreplaceable data until first-boot checks pass? — After the format, one external disk holds the only copy of coursework and uncommitted work, and review 2's risk was left open. — Recommendation: yes, keep a second copy of `Documents` and the key archives, even on a cheap USB drive or in private cloud storage, encrypted.
2. Which licence do the public repos get, or do they stay "all rights reserved"? — No top-level licence exists, and vendored code needs its notices kept. — Recommendation: MIT for your own code if you want others to reuse it, otherwise no licence. Keep third-party notices either way, and remove any font or image you cannot redistribute.
3. Should `~/.claude/projects` be encrypted on the disk? — Transcripts may contain secrets, which conflicts with keeping secrets off that disk. — Recommendation: yes, in an `age` archive with the same passphrase.
4. Should the new public repos keep the current names (`dotfiles`, `ai-dotfiles`, `quickshell-notch`)? — Keeping them minimises URL edits but makes old clones dangerous (finding 1). New names make old clones safe but require URL edits. — Recommendation: keep the names, and remove `origin` from all old clones first.

Technical recommendations I resolved myself: use `tar --compare` for archives, keep `self` bench semantics, add OVMF and swap to the VM, allow fixes during one pass and require one clean final run, make bootstrap re-runs safe, and set the `noreply` address in `.gitconfig`.
