# Plan review: opt-in packs (`ai-pack` + `pack-hint`)
Verdict: PASS WITH CHANGES
Summary: The idea and repo fit are sound. The weak spot is the core model: it treats every tool as per-project and checksum-pinned, but by the tools' own READMEs three of the six install account-wide (npm -g, the CBM binary and daemon, the plugin marketplace) and two cannot be checksum-pinned as planned. That breaks "remove leaves the project exactly as before" (demo priority 3). The estimates are about 2.5x low, but there is no deadline, so the scope fits.

## Findings
| # | Category | Severity (blocker/major/minor) | Finding | Evidence | Suggested fix |
|---|---|---|---|---|---|
| 1 | Technical correctness | major | The model has no account-wide layer. `@playwright/cli` installs with `npm install -g`. `codebase-memory-mcp` is one binary per account with a shared daemon and cache, and "all active CBM processes must run the exact same version". Adding a taste marketplace writes to `~/.claude/plugins/known_marketplaces.json`. None of these is per-project, so `remove` cannot "undo exactly" without counting which projects use each global install. | plan "Core model" l.39-46, "ai-pack CLI" Rules l.91; readmes/microsoft_playwright-cli.md:26; readmes/DeusData_codebase-memory-mcp.md:155,359 | Split each tool into `install` (global, one per machine, counted across projects in state) and `activate` (per project). `remove` deactivates; a global uninstall only happens when no project uses the tool any more, or behind an explicit `--purge`. |
| 2 | Technical correctness | major | `kind` has no `binary` value, yet codebase-memory needs download + sha256 (+ cosign) + placement on PATH before `claude mcp add`. `mcp` alone does not cover installing the binary. | plan "Core model" l.40; plan Research l.28 | Add `kind: binary` (url, sha256, dest `~/.local/bin`). Have the `mcp` tool list it in `requires`. |
| 3 | Technical correctness | major | "pinned source + checksum" cannot hold for `plugin` and `npm` as written. A marketplace plugin (`/plugin marketplace add Leonxlnx/taste-skill`) follows the repo's default branch. npm pins by version/integrity, not by our sha256. | plan l.40, l.98; readmes/Leonxlnx_taste-skill.md:98-99 | Vendor taste-skill as a `skill` at a reviewed commit (it is MIT), the same way as web-design-guidelines and Archify. For npm, pin the exact version and check npm's `integrity`. |
| 4 | Gaps (data/state) | major | `remove` "undoes exactly what add did", but nothing records what `add` actually did. Refcounts are derived from the current `packs.json`. If the manifest changes (a tool drops out of a pack, a version is bumped) or the user already had keys in `settings.local.json` (`enabledPlugins`, `env`), `remove` will leave orphans or delete the user's own values. | plan "Core model" l.43; Scope row l.113 | Store an add journal per project and tool: files created, JSON keys set with their previous values, claude commands run. `remove` replays it in reverse. Put a `schema_version` in `packs.json` and in the state files. |
| 5 | Gaps (versioning) | major | Vendored skills are symlinked from the dotfiles repo into each project. Every `git pull` of the dotfiles silently changes the active version in every project, while `projects.json` keeps the old version. There is no `update` or re-add path. | plan Scope l.113-114 | Record the version at activation. Have `list` flag a mismatch, and make `add` on an already-active tool a re-sync. Or copy instead of symlinking (this also survives moving the repo). |
| 6 | Gaps (concurrency) | major | Two sessions, or `ai-pack` running while a SessionStart hook reads state, can corrupt `projects.json`/`ignored.json`. Nothing is said about locking or atomic writes. | plan "Core model" l.43-44 | Use `flock` on `~/.local/state/ai-pack/lock` and write via temp file + `mv`. | 7 | Contradiction | major | Demo priority 2 says the hint "appears once", the `hint-shown` event exists, but no state stores it. The Rules say it fires on every `startup` until the user adds or ignores the pack. | plan l.46, l.65-66, l.147 | Either record `hint-shown` (per project and pack, with a timestamp, so it is shown once or once per N days) or change the demo text to "on every startup until added or ignored". |
| 8 | Gaps (drift) | major | No reconciliation when reality diverges from state: the user runs `claude plugin uninstall` or `claude mcp remove` by hand, deletes `.claude/skills/x`, moves or renames the project (state and local MCP are keyed by absolute path), or deletes the project. | plan "Core model" l.43; Research l.22 | `list` and `remove` check actual presence and tolerate missing pieces. Track the project by git root realpath. Add a `prune` step (or fold it into the LATER `doctor`). |
| 9 | Technical correctness | major | The hint's "< 1 s (cached file count)" has no cache location, key or invalidation. The `bigcode` rule "> 100k lines" needs reading every file, which cannot meet 1 s on exactly the big repos it targets. No `timeout` is given in hooks.json. | plan l.65, l.133 | Use only `git ls-files \| wc -l` (fast); cache under `~/.cache/ai-dotfiles/pack-hint/` keyed by repo path + HEAD; set `"timeout": 2` (or 3). | 10 | Technical correctness | minor | "No token cost" only holds if the hook prints `systemMessage` (as update-check does), not `additionalContext`. | plan l.34; plugins/toolkit/hooks/update-check.sh last line | State that the output must be `systemMessage`, and assert it in the test. |
| 11 | Gaps (git edge cases) | minor | `.git/info/exclude` breaks in worktrees and submodules (`.git` is a file there). It does nothing for already-tracked paths, e.g. a team repo that commits `.claude/`. The plan also does not say `settings.local.json` is excluded. A pre-existing `.claude/skills/<name>` would collide. | plan l.113 | Use `git rev-parse --git-path info/exclude`. Exclude every path ai-pack creates. | 12 | Gaps (project-local side effects) | minor | Some tools write into the project at run time and `remove` will not undo it: playwright-cli reads `.playwright/cli.config.json`, which is where the system-Chromium `executablePath` would live; CBM can write `.codebase-memory/`; Archify writes HTML output. ## Unnamed risks
- Local-scope MCP/settings are keyed by exact path; launching `claude` from a subdirectory, or through a symlinked path, may not see them — medium — verify early; resolve the git root realpath; document "start claude at the repo root".
- Claude Code may not follow symlinked skill dirs consistently, or the dotfiles path may move or be renamed — low/medium — copy instead of symlinking, or test the symlink at the start of implementation.
- CBM's account-wide version lock: an `install` run by CBM's own updater or another agent can break the pinned binary for all projects — medium — never run CBM's `install`/`update`; register manually; pin the version in upstreams.json.
- Taste-skill and Archify do network work at run time (image search, daily update check), which goes against "reviewed and pinned" — medium — set `ARCHIFY_UPDATE_CHECK_DISABLED=1` in env; document taste's network use.
- Plugins enabled per project still change the global update-check hook's output (installed_plugins.json) — low — confirm update-check tolerates local-scope entries; add a test.
- The `require-check` Stop hook keeps running in target projects; ai-pack edits under `.claude/` leave the dotfiles repo untouched, but tests that write fixtures inside the repo would make the tree dirty — low — keep all fixtures under mktemp.

## Questions for the user (max 5)
1. Is github.com/FreidhYMorales/ai-dotfiles public? — It decides whether unlicensed or brand files can be committed (finding 15). — Recommendation: if public, fetch these at `add` time from a pinned commit + sha256; do not commit them.
2. When the last project using a global tool (playwright-cli, codebase-memory binary) runs `remove`, should ai-pack uninstall it from the machine or leave it? — It defines what "exactly as before" means for demo priority 3. — Recommendation: leave it installed; remove it only with `--purge`.
3. Should the startup hint show once per project, or on every startup until you add or ignore the pack? — The plan contradicts itself here (finding 7). — Recommendation: once per project and pack, again only after 30 days.
4. Is it OK to vendor taste-skill as a pinned skill instead of installing it from its plugin marketplace? — Removes the unpinned marketplace and most of the `plugin` kind's work. — Recommendation: yes, vendor it.
5. Should vendored skills follow the dotfiles repo automatically (symlink) or stay frozen per project until re-added (copy)? — Trade-off between staying current and reproducibility (finding 5). — Recommendation: copy, and have `list` flag version drift.
