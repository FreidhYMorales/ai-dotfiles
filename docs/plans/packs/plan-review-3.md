# Plan review: opt-in packs (`ai-pack` + `pack-hint`), review 3
Verdict: PASS WITH CHANGES
Summary: The plan resolves every finding from reviews 1 and 2. I checked each resolution row against the plan body and all are present. Review 2's open items also hold up against the repo: `check-skills.sh` only scans `plugins/*/skills`, `run-tests.sh` only runs tests under `plugins/` and `scripts/`, and `install.sh` already links every `bin/*`. I found four new major gaps, all about what is left over after things go wrong: `info/exclude` is shared across git worktrees, an interrupted `add` leaves files the journal does not know about, deleted projects keep their refcounts so `--purge` can never run, and the collision rule blocks the common case where `settings.local.json` already exists. There are no blockers, and the scope fits because there is no deadline.

## Findings
| # | Category | Severity (blocker/major/minor) | Finding | Evidence | Suggested fix |
|---|---|---|---|---|---|
| 1 | Technical correctness | major | `git rev-parse --git-path info/exclude` gives the same file for the main worktree and every linked worktree, because `info/` lives in the common dir. If both worktrees have `web` active, `remove` in one deletes exclude lines the other still needs, and its `.claude/skills/...` files then show up as untracked. The test row includes a worktree but does not cover this. | plan "ai-pack CLI" Rules l.118 and l.121; Scope l.158; `man gitrepository-layout`: "info … is ignored if $GIT_COMMON_DIR is set and "$GIT_COMMON_DIR/info" will be used instead" | Journal exclude lines keyed by the resolved exclude-file path, with a refcount across projects. Remove a line only when the last project using that file drops it. Never add (or later remove) a line that was already there. Add a test with two worktrees. |
| 2 | Gaps (retries / interruption) | major | Rollback only covers a failure that the code catches. If a run is killed (Ctrl-C, terminal closed, crash) after some writes but before the journal is saved, files are left that the journal does not know about. The next `add` then refuses ("target exists and is not in the journal"), and `remove` has nothing to replay. The project is stuck. | plan Rules l.117, l.121; Core model l.58-60 | Write the journal ahead of each change: record the intended entry (status `pending`) under the lock before the write, and mark it done afterwards. Add a trap on INT/TERM that rolls back. On the next run, treat `pending` entries as ours and roll them back or finish them. Add a test that kills the run partway. |
| 3 | Gaps (drift) | major | `list` skips projects whose root no longer exists, but `machine.json` still counts them. `--purge` refuses whenever other projects use the tool, with no override, and `prune` is LATER. So once one project that used the tool is deleted or moved, the tool can only be purged by editing state by hand. | plan Rules l.119, l.123; Scope l.166; resolution review-2 #9 l.244 | When checking whether `--purge` may run, ignore refcounts from projects whose root is gone, and drop those entries under the lock, as `list` already does. It also conflicts with the journal model, which stores "JSON keys set (value written + previous value)" and so assumes merging into an existing file. | plan Rules l.121; Core model l.59-60; Scope l.155 (Archify env) | Apply the collision rule only to whole files and directories that ai-pack creates. ## Unnamed risks
- Arch's rolling `chromium` can run ahead of the browser build that `@playwright/cli` 0.1.22's playwright-core expects, which can break CDP calls — medium — in the manual check, run a real `playwright-cli open` against system Chromium and record the working pair in docs/packs.md.
- Claude Code rewrites `.claude/settings.local.json` itself (permission approvals) while a session is open, which can race with ai-pack's write or drop its `env` key — low — have `list` check that each key is really there (already planned) and tell the user to run `add`/`remove` with Claude closed in that project.
- The global gitleaks pre-commit hook (install.sh `install_git_hooks`) scans the vendored third-party trees, and a test fixture that looks like a secret would block the vendoring commit — low — run `gitleaks` on `packs/vendor/` before committing; keep any allowlist narrow.
- Three `startup` hooks (update-check, backup-status, pack-hint) now all emit a `systemMessage`, so the hint can get lost among the others — low — keep the hint to one line and check how it renders in the manual check.

## Questions for the user (max 5)
1. `--purge` currently refuses with no override. May it ignore projects whose folder no longer exists, and clear their entries? — Without this, one deleted project blocks purging that tool forever until `prune` lands (finding 3). — Recommendation: yes; still refuse for projects that exist.
2. Which `DESIGN.md` brand files should `web` fetch, and where should they land in the project, or should they move to LATER? — They are in the MUST scope but no tool owns them (finding 9). — Recommendation: move them to LATER unless you have a specific brand in mind for a current project.
