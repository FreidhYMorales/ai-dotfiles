## Findings
| # | Category | Severity (blocker/major/minor) | Finding | Evidence | Suggested fix |
|---|---|---|---|---|---|
| 1 | Technical correctness | major | "Built in a staging dir beside it and moved into place with `mv`" breaks on re-sync and on the version bump. When `<target>` already exists as a dir, GNU `mv staging target` moves staging *into* the target and gives `.claude/skills/archify/.staging-x/`. That nested copy is a second SKILL.md with the same frontmatter name, and the "tree hash ok" check fails from then on. Re-sync (`add` on an active tool) and the "3.2.0 -> 3.3.0" upgrade path always replace an existing dir. | plan Core model l.58; CLI Rules l.121 ("re-sync"), l.124; screen l.108 | Use `mv -T` for first installs, so the move fails instead of nesting. For replacement, use `mv --exchange staging target` (coreutils >= 9.5 on Arch), then remove the old copy. The fallback is `mv -T target old && mv -T staging target`. Add a re-sync test that asserts no nested dir. |
| 2 | Gaps (runtime side effects) | major | Runtime output collides with the whole-dir model. (a) playwright-cli writes snapshots to `.playwright-cli/` in the cwd. That dir has no self-ignoring `.gitignore`, so it shows up in the project's `git status`. Demo 1 ("shows nothing new") and leftovers l.131 only name Archify. (b) If `outputDir` is pointed inside `.playwright/`, the dir's tree hash changes after the first run. `remove` then treats it as hand-edited and leaves it (l.125), which breaks demo 3. Skills that write state or cache into their own dir (taste-skill scripts, Archify reminder state if the patch misses one) have the same problem. | readmes/microsoft_playwright-cli.md:330 (`.playwright-cli/page-*.yml`), :418, :501-508 (`outputDir`); plan l.56-57, l.125, l.131, Demo priorities l.206, l.208 | Journal and hash only the files ai-pack wrote (a file list with per-file sha256), not the whole dir. On `remove`, delete those files if they still match, then delete the dir only if it is empty apart from declared `leftovers`, which are printed. Declare `.playwright-cli/` as a leftover. Either set `outputDir` to a subdir of the self-ignoring `.playwright/` or document the root path (see Q1). Add to the manual check: "run a real snapshot, then `git status` and `ai-pack remove web`". |
| 3 | Contradiction / technical correctness | major | "Network error -> nothing written" and "preflight ... downloads before any write" do not hold for kind `npm`. `npm pack` fetches only the top tarball. Installing it into `~/.local/share/ai-pack/npm` then fetches the transitive deps over the network after preflight, and can fail halfway. Rollback only covers "dirs moved in this run", so a failed install leaves a partial prefix with no `machine.json` entry. A failed upgrade can also break the tool for every other project, because the layer is machine-wide (l.128). | plan l.123-124, l.134, l.49-50, l.160; Data gaps l.190 | Install each version into its own prefix (`.../npm/<tool>@<ver>.staging`), using `--ignore-scripts`. When it succeeds, `mv -T` it to `<tool>@<ver>` and switch the bin link atomically (`ln -sfn` to a temp name, then `mv -T`). Record it in `machine.json` only after that. On failure, delete the staging prefix. Add a test where the network fails during the npm install. |
| 4 | Technical correctness | minor | The tree hash includes the full file mode, and `cp -a` copies modes from a git checkout. Those modes depend on the umask (644 vs 664), so a pinned hash computed on one checkout can fail on another. That gives a false "integrity mismatch" and a refusal. | plan Core model l.60; Scope l.159 | Hash only the exec bit (x / -) and the file type, not the full mode. Set the mode explicitly (`chmod`) after the copy. |
| 5 | Gaps (interruption) | minor | The staging dir "beside" its target sits inside `.claude/skills/`. A running Claude session may load it as a duplicate skill, and a killed run leaves it there. Adoption only covers the final targets, and nothing cleans stale staging dirs. | plan l.58, l.124 | Stage under one fixed name pattern (for example `<parent>/.ai-pack-stage-*`) that holds no SKILL.md until the move, or that starts with `.gitignore`. Delete stale `.ai-pack-stage-*` under the lock at the start of every `add`/`remove`. Extend the killed-run test to cover it. |
| 6 | Contradiction | minor | Adoption runs "on the next `add`/`list`", which writes the journal. The plan also says `list` "skips projects whose root no longer exists (no state write)", which reads as "`list` is read-only". It is unclear whether `list` takes the write lock. | plan l.124 vs l.130 | Make `list` read-only: it shows "adoptable" and `add` does the adoption. ## Unnamed risks
- The hook relies on `ai-pack` being on PATH, but Claude started from a desktop launcher or a non-login shell may not have `~/.local/bin` on PATH, so the hint never fires and nobody notices — medium — have the hook fall back to `${XDG_BIN_HOME:-$HOME/.local/bin}/ai-pack`, and check it during the manual check.
- The toolkit plugin version (hook in the plugin cache) and the repo's `bin/ai-pack` can skew. After an older toolkit or a newer repo, `hint --cwd` may change its interface and the hint goes quiet — low — keep `hint --cwd` as part of the frozen contract and give the hint output a version.
- The machine-wide npm upgrade swaps playwright-cli while other Claude sessions are using it, which can break a browser run mid-session — low — the per-version prefix (finding 3) leaves the old version in place until the bin link switches. Remove old prefixes only on `--purge`.
- An Arch `nodejs` upgrade past the version that taste-skill or Archify scripts were tested with fails at run time, not at `add` — low — record the tested node version in docs/packs.md next to the Chromium pair.

## Questions for the user (max 5)
1. Where should Playwright's runtime output go: inside the self-ignoring `.playwright/` (needs per-file hashing, finding 2), or in the default `.playwright-cli/` at the project root, listed as a leftover? Today the default dir shows up in the project's `git status`. — It decides whether demo 1 ("nothing new in git status") and demo 3 (clean remove) can both pass. — Recommendation: `outputDir: ".playwright/output"` plus per-file hashing, so everything stays in one self-ignoring dir.
2. When `remove` finds a hand-edited copy, should ai-pack forget it (the copy stays and the tool stops counting as used), or keep tracking it (which blocks `--purge`)? — Without a rule, the project ends up stuck either way (finding 7). — Recommendation: forget it and print the path to delete.
