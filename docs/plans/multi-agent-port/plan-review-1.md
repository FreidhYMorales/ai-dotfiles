# Plan review: multi-agent-port
Verdict: PASS WITH CHANGES
Summary: The direction is sound (one source, a generator, a core script per hook plus a thin adapter for each agent), and with no deadline the scope fits. But item 0's premise contradicts the agy 1.4.7 docs installed on this machine, and the plan would delete or overwrite files that other tools own (`~/.gemini/GEMINI.md`, the herdr hooks, engram.ts). Several hook adapters would also do nothing without anyone noticing, because the agy and OpenCode inputs have no `cwd` or `source` field and no prompt event. All of these can be fixed before coding starts.

## Unnamed risks
- **The agy docs conflict.** The web docs (the plan's source) and the docs bundled with 1.4.7 disagree on global paths. The installer could write to paths agy never reads, so the setup looks done but rules, skills and agents don't load. Likelihood: high. Mitigation: test each path with a sentinel file (finding #1).
- **Hooks that fail open.** Every core script exits 0 on bad input or a missing cwd, so a broken adapter looks exactly like "the check passed". Likelihood: high. Mitigation: per-adapter golden tests with real payloads; the smoke test must show a block and a Stop refusal in each agent.
- **Stop-hook loop in agy.** `decision: continue` with no reentry guard keeps re-entering until `MAX_FORCED_INVOCATIONS`, and burns quota. Likelihood: medium. Mitigation: map reentry from `executionNum`.
- **OpenCode plugin API v2 migration.** It could break the TS plugin and engram.ts on the next OpenCode update. Likelihood: medium. Mitigation: pin the version in the docs, and have `make check` type-check the plugin with deno/node (both installed).
- **Running out of quota mid-smoke.** The full SDD `new`→`archive` cycle in two agents is expensive, and the plan exists because quota runs out. Likelihood: medium. Mitigation: a tiny toy change, and run the smoke on cheap models (`flash`).
- **Gentle-ai fights back.** gentle-ai updates may rewrite `~/.gemini/GEMINI.md`, the skills or `opencode.json`, undoing the installer's changes. Likelihood: medium. Mitigation: the installer is idempotent, warns on drift, and documents how the two coexist.

## Questions for the user (max 5)
1. Do you still use Gemini CLI or gentle-ai's `~/.gemini/GEMINI.md` anywhere? Removing it may break that tool. My recommendation: don't delete it; leave it unless the test proves agy loads it, and then ask before removing.
2. When gentle-ai copies of the same skills exist (`sdd-*`, `judgment-day` in `~/.gemini/skills`), should this repo's versions always win? This decides whether the installer shadows them, deletes them, or leaves them alone. My recommendation: shadow them through precedence, never delete.
3. Is it acceptable that in OpenCode the `make check` Stop gate becomes only an instruction (no hard block)? My recommendation: accept it for v1 and add a rule line telling the agent to run `make check` before saying it is done.
4. Should `pause` work in agy for v1, even though agy has no prompt hook? My recommendation: OpenCode only in v1; in agy, say "pausa" and rely on a rule line.
5. Should `install.sh` or `ai-update` also regenerate and re-link the OpenCode/agy outputs on every update, so they never go stale? My recommendation: yes, `ai-update` calls the generator plus the install steps for each target.

Technical recommendations I resolved myself (no input needed): gitignore the build dir and add a staleness check in `make check`; use a jq merge of a named `toolkit` key in agy `hooks.json`; quote generated paths because the repo path contains a space; prefix generated commands; leave `engram setup` out of the installer and only verify.
